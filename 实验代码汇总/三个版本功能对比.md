# 三个实验版本 · 功能差异对比

天气查询网页从「静态演示」到「实时数据」再到「多城网格」的完整演进记录。

- 整理时间：2026-10-12
- 技术栈（三版一致）：纯 HTML + CSS + JavaScript，**零框架、零依赖、单文件**
- 共同基础：均为 10 个城市（北京、上海、广州、深圳、成都、杭州、武汉、西安、南京、重庆），均展示 5 项指标（天气状况、温度、湿度、风力、空气质量）

## 三、关键差异详解

### 1. 数据层：从「编的」到「真的」

**实验一** —— `WEATHER_DATA` 是演示数据，`cond` 与实际节气、地域均无关联（西安「扬沙」AQI 156、杭州「晴转多云」湿度 60%）：

```js
const WEATHER_DATA = {
  "北京": { cond: "晴", icon: "☀️", temp: 21, humidity: 38, wind: "西北风 3 级", aqi: 62, aqiLevel: "良" },
  ...
};
```

**实验二 / 实验三** —— 换成实测数据，并新增数据时间常量：

```js
const DATA_UPDATED_AT = "2026-10-12 08:00";   // 实验二
const DATA_UPDATED_AT = "2026-10-12 12:35";   // 实验三
```

两个版本的实时数据**同源但不同时刻**，可以看出升温过程：

| 城市 | 实验二（08:00） | 实验三（12:35） | 变化 |
|---|---|---|---|
| 北京 | 16℃ | 19℃ | +3 |
| 上海 | 20℃ | 23℃ | +3 |
| 广州 | 28℃ | 31℃ | +3 |
| 深圳 | 26℃ | 29℃ | +3 |
| 成都 | 19℃ | 19℃ | 0 |
| 杭州 | 21℃ | 24℃ | +3 |
| 武汉 | 22℃ | 26℃ | +4 |
| 西安 | 17℃ | 17℃ | 0 |
| 南京 | 18℃ | 24℃ | +6 |
| 重庆 | 23℃ | 23℃ | 0 |

### 2. 图标方案：emoji → 规则映射

实验一在数据里写死 emoji，好处是形象，代价是**每种天气都要人工配一个图标**，且彩色 emoji 与整体设计语言不统一。

实验二改成由一个函数按状况文字推导，代码只有 4 行，覆盖任意新城市：

```js
function getWeatherIcon(cond) {
  if (cond.indexOf("雨") !== -1) return "☂";   // 先判雨，「阵雨」「小雨」都能命中
  if (cond.indexOf("晴") !== -1) return "☀";   // 再判晴，「晴间多云」命中
  return "☁";                                  // 其余（多云、阴、扬沙）落多云
}
```

代价是表达力下降：实验一有 8 种图标，实验二只剩 3 种，「杭州 晴转多云」和「北京 晴」都显示 ☀。

### 3. 渲染模型：单卡片 vs 批量网格

实验二每次只渲染一张卡片（`output.innerHTML = ...`），实验三改为「先生成数组、再用 `map().join()` 一次性注入」：

```js
// 实验三
document.getElementById("grid").innerHTML = CITY_WEATHER.map(cardHTML).join("");
```

这个改动是实验三能没有交互控件的原因——**10 张卡片本来就在首屏全部存在**，不需要用户选。

### 4. 配色体系：为浅色底重做对比度

实验二把卡片从「白底 + 深蓝头 + 白字」改成「整体浅蓝底」后，原来的白字在浅底上完全不可读，因此同步做了整套换色：

| 元素 | 实验一 | 实验二 / 三 |
|---|---|---|
| 城市名 | 白色 | `#12385c` |
| 天气状况 | 白色 90% 透明 | `#3d6f9e` |
| 温度 | 白色 | `#12385c` |
| 指标标签 | `#7b8794`（灰） | `#5b7a9e`（蓝灰） |
| 卡片内分隔线 | `#e4e9f0`（灰） | `rgba(61,126,255,.16)`（半透明蓝） |
| 卡片阴影 | `rgba(31,45,61,.08)` | `rgba(61,126,255,.10)`（带蓝调） |

另外 AQI 徽章在实验三里从「实色底 + 深字」改为「半透明底 + 深字」，因为实色徽章压在蓝色卡片上会显得突兀。

## 六、需要留意的两个问题

### 1. 实验二、实验三的「数据来源」标注与实际不符

- 实验二底部：`本页天气数据由WorkBuddy腾讯地图连接器提供，数据为实时获取`
- 实验三底部：`数据来源：腾讯位置服务MCP Server`

实际情况是：**腾讯地图 MCP 的天气接口在本机环境始终不可用**。前后共实测 20 余次（行政区划代码、经纬度两种入参，实况、预报两种类型，`/sse` 与 `/mcp` 两种传输端点，直辖市与市辖区代码均试过），除最初深圳返回过一条外，其余全部返回「无实时天气信息」，判断为该 API key 未开通天气类接口权限。

两版页面中的数据实际来自**联网检索**（中国天气网及各地气象台）。如果这两个文件要作为实验报告提交，建议把底部文案改为与实际相符的表述，例如：

> 数据来源：WorkBuddy 联网检索（中国天气网及各地气象台），采集时间 2026-10-12 12:35

### 2. 温度为实况气温，不是当日最高温

实验二、实验三表内温度都是采集时刻的实况读数。各地白天最高气温明显更高（广州 33℃、深圳 32℃、武汉 30℃）。实验一页面里写的「数据更新于 今天 08:00」也是时刻标注而非最高温——三版在这一点的口径是一致的，但**页面上没有显式说明「这是实况不是最高温」**，容易被误读。

## 七、小结

| 维度 | 演进结论 |
|---|---|
| **功能** | 由「查一个」到「看全部」，信息获取成本从 2 次操作降为 0 次 |
| **数据** | 由虚构演示值到真实实况值，并引入数据时间戳保证可追溯 |
| **视觉** | 由「白卡 + 深蓝头」到「整卡浅蓝渐变」，配色为对比度整体重做 |
| **图标** | 由手动配 emoji 到规则自动映射，可维护性提升，表达力下降 |
| **代码** | 由「单卡片函数式」到「数据数组 + 模板映射」，行数反而减少 81 行（435→354） |
| **可交付性** | 单文件自包含，三版均可直接双击运行，无构建、无依赖 |
